# Servidor privado Node de producto

Preparación interna posterior a PR404/main5ba3e54. Autorización vigente de implementación continua e inline. Sin montaje, claves nuevas, migraciones ni activación remota.

El servidor deja de depender de un entrypoint de fixture. El build genera un programa autocontenido y SHA-256 reproducible, sin secretos. Al iniciar, Node exige bootstrap privado de descriptor exacto y capacidad de servicio de32bytes; borra la variable de entorno y contrasta el hash del programa realmente recibido por `-e` antes de escuchar. Esto no acredita origen de plataforma ni borrado seguro del entorno del proveedor. La revisión de fuente se fija después del merge; el nombre de imagen no acredita digest inmutable.

El puerto privado8080 ofrece únicamente preparación firmada y despacho mediante el puente existente. La preparación usa desafío aleatorio, plazos de5s limitados por el lease original y propósitos HKDF distintos para solicitud/respuesta. La aceptación del host es de un solo uso, verifica todos los campos originales y no permite reflexión o cambio de programa. Todavía requiere observación real del Container y permiso primario actual por parte del host.

El consumo siempre va a `http://afw-node-control.internal/consume`; no hay selección de destino, sender, TLS o DNS en el API de producto. El callback usa el transporte HTTPS nativo existente. Cuerpos reales limitados a2048bytes y UTF-8 estricto, headers8KiB y5s por solicitud, errores constantes. Un cuerpo incompleto reproduce un socket retenido; la corrección aborta y destruye la entrada al vencer el plazo. Al desconectar se cancela el trabajo. No reintenta ni reconstruye confirmaciones perdidas.

Revisión fresh única: un Important por headers incompletos anteriores al callback `request`. El timeout periódico nativo no aseguraba5s. Reproducción RED propia y del revisor; ahora un timer absoluto al aceptar cada socket cubre headers y cuerpo juntos, sin renovarse por datos/goteo. Se comprobaron headers sin terminar y headers completados tarde seguidos de cuerpo parcial; al quitar el guard en reproducción controlada la segunda prueba falla. No nueva revisión ni cambio de plazo de producción.

La vida del proceso se fija al arrancar con `performance.now()`. El cierre aborta peticiones y cierra conexiones. Un retroceso del reloj de pared no prolonga el timer original. SIGTERM/SIGINT solicitan el mismo cierre. La prueba de proceso hijo comprueba salida real; no equivale a confirmación de stop del proveedor alojado.

Pruebas: Node hijo ejecuta el programa de producto con bootstrap en env; hash incorrecto/descriptor inválido salen con mensaje constante, preparación firma manifiesto original, entradas demasiado grandes/mal codificadas fallan, cuerpo incompleto libera socket y proceso termina al lease. El retroceso de reloj es una modificación exclusivamente del bundle de test, con hash propio; no hook de producción. Estos datos/identidades son sintéticos y locales. La entrega pública y correlación con turno cloud siguen pendientes.
