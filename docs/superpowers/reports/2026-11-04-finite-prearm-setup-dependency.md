## Finding: the current full-policy requirement creates a causal cycle

The proposed third owner publication cannot require the genuine full private canaryLive policy produced by the current setup builder. That builder depends on primary T0 and selected owner preparation, while selecting that preparation already requires the third publication.

Actual path, not a fixture inference:

1. [readPreparationFacts](https://github.com/tokenizartinfo-ops/agent-friendly-web/blob/aed54dab23b644481aed01cf6b5b94249ecf9f23/lib/mcp-qa-finite-owner-preparation.mjs#L425) requires source.phase === 'finite_prearm', exact three-stage history and current grant/notice facts. createFiniteConnectionPreparation({ctx,env}).run(refs,originalLease) only publishes OwnerPreparation/Selection after the actual finite-stage transport returns installed and these facts pass.
2. [readFiniteOwnerSetupFacts({ctx,env,intentId,sourceRevision},originalLease)](https://github.com/tokenizartinfo-ops/agent-friendly-web/blob/aed54dab23b644481aed01cf6b5b94249ecf9f23/lib/mcp-qa-finite-owner-preparation.mjs#L461) reads source + material, then requires selected.preparation, its witness and selection timestamps <= primary T0, T0 < commandBy, and the third receipt completed before selection. 3. [readFiniteSeedPrimary({get,seed,phase,now})](https://github.com/tokenizartinfo-ops/agent-friendly-web/blob/aed54dab23b644481aed01cf6b5b94249ecf9f23/lib/mcp-qa-finite-seed-primary.mjs#L17) derives T0 from the exact original issue-comment created_at, not an owner request clock or guessed future timestamp. readFiniteMaterialSeed(options) verifies the corresponding seed/tag, completed seed-material step and source lineage. Thus: third full policy -> setup T0/facts -> selected preparation -> third receipt. Current source has no alternative real pre-T0 full-policy producer in this callgraph. readPrivateQaFiniteConnectionSource, readPrivateQaFinitePolicyEntry and readPrivateQaFinitePolicySource are unavailable stubs. The real derive implementation is present, but not a qualified mounted source producer. The historical SYNTHETIC-PRIVATE-* fixture does not close this gap.

## Recommended correction, for root source-design acceptance

Separate a strictly closed third owner configuration from the later genuine full private setup publication. The phase finite_prearm describes accepted original preparation/three-stage history, NOT full private policy installation or nominal permission.

The smallest closed prearm configuration is the original capsule M preparation configuration, restored byte-for-byte at the configuration level from the qualified original plan: OAuth/monitoring and every nominal enable flag false; four nominal policy strings and monitoring policy empty; original project/client, Access, expiry, limiter, physical bindings, metadata binding, exports/container declaration and module bytes retained. The actual third ConnectionReceipt must still be new and linked to its exact predecessor, decision, grant and notice; equality to original config does not erase that third publication history or permit replay.

This leaves the first two publication changes restricted to their existing three-setting family. No new module, binding namespace, clock, Entry, actor or generic authorization mechanism is required for prearm. Do not make empty text pass projectFinitePublicConfiguration('canaryLive') and do not pass finite_prearm to qualifyFiniteConnectionProfile. Instead use a separate exact closed-prearm qualifier, which can verify the underlying closed_ui preparation shape plus equality to original qualified configuration while the phase source verifies the distinct finite-stage receipt.

**Necessary additional change in setup:** today's derive only clones source.baseline.configuration and replaces six private slot values. It DOES NOT enable the three nominal full-profile flags or change binding shape. Merely making the third stage closed would therefore leave setup failing its full projection. The setup builder must deliberately construct the distinct full candidate from the accepted fixed canaryLive template and the qualified original physical holders, filling only its six fixed private slots from genuine derive facts. The current full template enables events/successor/permission-withdrawal, keeps OAuth/refresh/monitoring/save/schedule/retirement-read closed and requires nonempty private-slot text.

There is also a binding-shape distinction that must be explicit: the initial preparation builder adds ACCESS_TEAM_DOMAIN, ACCESS_AUD, AFW_OAUTH_PILOT_EXPIRES_AT, DELEGATED_RATE_LIMITER and AFW_DOSSIER_MONITORING_OWNER_POLICY. The full canaryLive projection accepts NONE of these five additional preparation bindings. Under this recommendation they remain unchanged through all three owner stages; the separate setup full publication removes exactly these five preparation-only bindings. All persistent DO namespace/KV/D1/secret identities and remaining fixed values are independently checked; no new secret is needed. DELEGATED_RATE_LIMITER is a ratelimit binding, not plain text: its removal is an explicit preparation-limiter reference change and must not be described as preserving every physical binding. If “bindings unchanged” means every binding name forever, that stronger invariant is incompatible with the current full projection and needs a separate design change. Do not silently claim both.

The configuration path would be:

original M closed preparation -> read_consent -> notice_consent -> exact closed prearm -> genuine T0/seed/setup -> distinct full PolicyReceipt -> separately qualified nominal setup/handoff.

This is a recommendation, not an observed positive prearm flow. Two-phase context work remains unchanged and later phases remain unavailable until the future source/test gates exist.
