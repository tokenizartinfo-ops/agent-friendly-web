# Permiso específico para avisos del expediente — fuente cerrada

El permiso OAuth de lectura no significa consentimiento para seguimiento. Este bloque prepara un journal distinto, `afw.dossier-monitoring.v1`, y compone su lectura primaria con el controlador finito de suscripciones aceptado. No instala una pantalla, endpoint, migración remota, namespace, clave ni permiso real.

## Registro y autoridad

`db/dossier-monitoring-consent.sql` es aditivo, destinado al D1 privado del expediente. Conserva dueño, proyecto, conexión OAuth, cliente, recurso, revisión inicial, propósito, solicitud, emisión y vencimiento. UPDATE/DELETE del journal están bloqueados mediante triggers. Eso no acredita protección contra un administrador que elimine/restaure el almacenamiento o sus triggers: la custodia e historia del host siguen siendo un gate.

`recordDossierMonitoringConsent` solo admite opciones resueltas por el futuro adaptador autenticado del owner. Ese adaptador debe comprobar identidad, CSRF, cuerpo acotado, despliegue/ventana propia y conexión/proyecto seleccionados en servidor. No exponemos esta función como HTTP ni inferimos una elección del usuario. Copia actor y parámetros antes de esperar. La inserción comprueba en una única sentencia dueño actual, conexión activa, scope de lectura, revisión inicial, límite original OAuth y secuencia esperada. Un grant explícito dura hasta diez minutos; otro grant para la misma conexión queda denegado incluso tras retirar o vencer. Retirar conserva historia y se permite con identidad del owner vigente aunque el monitoreo o la conexión OAuth hayan vencido; no autoriza lecturas con un token inválido.

La repetición de la solicitud devuelve el recibo histórico de la misma operación sin renovar su plazo. Un recibo de grant no certifica que el permiso continúe activo: para eso se consulta la autoridad actual. Una nueva revisión del expediente es precisamente el evento observado; no exige ampliar el permiso, pero un cambio de dueño, cliente, recurso, scope, conexión o retirada sí impide autorizar avisos.

`createDossierMonitoringAuthorization` recibe exclusivamente contexto de un host OAuth que ya validó el token. Consulta conjuntamente el grant actual, dueño y propósito original desde sesiones `first-primary`, sin caché, y vuelve a leer tras la espera para rechazar deriva. Comprueba el reloj y el vencimiento después de consultas y proyección. El selector del proyecto se obtiene con `projectDossierEvent` y el mismo secreto de proyección original del productor; no se inventa a partir de un ID enviado por cliente. Las referencias de principal, recurso y permiso usan dominios separados. Su mínimo de plazo OAuth/consentimiento limita el controlador.

`createDossierMonitoringEventsAuthority` enlaza ese resolver con list/subscribe/unsubscribe/deliver reales del controlador. El almacenamiento y custodia se suministran por el host: UNA autoridad dedicada de QA conserva el presupuesto global, nunca un pool de clientes. `deliver` solo pertenece al productor interno de metadata original; no se agrega un método MCP que permita a un cliente inventar eventos. El adaptador privado de PR397 puede recibir esta autoridad cuando exista el montaje autenticado correspondiente. El Worker OAuth actual continúa sin flag ni binding de eventos.

## Evidencia y próximos gates

Pruebas en SQLite nativo verifican permiso de lectura sin promoción, consentimiento finito/idempotente, retirada terminal, historial inmutable, cambios de dueño/cliente/scopes/conexión, vencimiento después de await, CAS concurrente y snapshot del actor. Prueba nativa workerd compone D1 real y Durable Object SQLite real con el controlador: catálogo cerrado, grant de fixture, un challenge, repetición sin reenvío, retirada y suscripción denegada. Contexto OAuth y respuesta externa son fixtures sintéticos, no consentimiento/token/callback reales. Se aplica el SQL de journal completo, incluidos triggers.

Faltan el adaptador humano de consentimiento y el binding del mismo OAuth autenticado, protección de custodia/historia, DO→Node alojado con admisión durable por bytes/fase consumida antes de envío y sin reconstrucción tras pérdida de ACK, montaje propio cerrado y aceptación real de plugin/callback/revisión cloud terminada. Después: una ocurrencia alojada propia, retirada/cierre independientes y PC-off acordado. Max mantiene preview de invitación aprobado, ingreso y consentimiento propios. Nada de esta preparación acredita guardia permanente ni permite enviar el primer mail a Max.
