# Watchdog independiente: runtime cerrado

Proyecto AFW, repositorio agent-friendly-web. `worker/operations-watchdog/index.mjs` conecta la lectura de constancias con el registro transaccional de [transiciones](AFW-WATCHDOG-TRANSITIONS-2026-10-04.es.md). Worker dedicado `agent-friendly-web-operations-watchdog`, separado del productor y del consumidor de investigaciones. No ejecuta reparaciones, no consulta expedientes y no envía avisos.

Config canónica `wrangler.operations-watchdog.jsonc`: flagfalse, sin deadline, cron vacío, workers.dev/previews deshabilitados, sin rutas, secretos o bindings externos. Binding exclusivo OPERATIONS_STATE_DB a D1 operaciones603c471d-19bb-4530-9773-c02e18b29840. Pausa/configuración/versiones son variables del servidor, nunca argumentos HTTP. El fetch siempre404, incluso si está habilitado; solo scheduled puede iniciar el recorrido. No hay nueva identidad de servicio o autorización del usuario por una URL.

Antes de IO exige flag habilitado y deadline canónico vigente. Exige estado del productor explícitamente true/false y binding prepare/batch válido. Lee mediante sesión first-primary cuando D1 la ofrece, calcula condiciones saneadas y vuelve a comprobar el reloj real antes de persistir. Un vencimiento durante la lectura impide las escrituras siguientes; no cancela un batch ya admitido. Errores de almacenamiento se sustituyen por mensaje fijo. Pausa del productor registra estado paused sin consultar checkpoints ni crear avisos.

El flag y las versiones del productor NO se sincronizan automáticamente con control plane. La futura activación deberá resolver y verificar configuración del servidor con evidencia actual; este runtime no acredita monitoreo fiable con bindings obsoletos. Una modificación externa de intención requiere reconciliación explícita antes de afirmar vigilancia. La configuración cerrada no constituye esa reconciliación continua.

Pruebas SQLite del recorrido completo: cierre/deadline sin IO, fetch404, constancias ausentes y avisos deduplicados, pausa sin lectura/aviso, configuración desconocida/error saneado y deadline que vence durante lectura sin persistencia. El esquema watchdog sigue con su recibo remoto independiente: ni código ni dry-run prueban migración, publicación, cron remoto o entrega de avisos.

Publicación cerrada y aplicación aditiva, cuando se efectúen, requieren preflight del recurso/DB y conservar historial. Rollback: flagfalse, deadline ausente, schedules[], sin rutas/secretos; conservar tablas, checkpoints y avisos, nunca DROP. Registrar versiones y conteos comprobados en recibo separado. No reabrir manager/token para publicar este Worker cerrado.

Siguiente: aceptación remota sintética con D1 de QA aislada para fixtures (no modificar constancias históricas de operaciones), ventana que contemple propagación de cron y cierre verificable.
