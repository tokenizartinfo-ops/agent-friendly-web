# Instalación privada del catálogo QA

El instalador prepara una sola inscripción V2 propia con aprobación D1 primaria y publicación atómica del puntero lector, registro QA y reserva de identidad en el DO. `install()` no acepta autoridad del llamador: usa únicamente fuentes administrativas privadas preconfiguradas. No está importado ni expuesto por el Worker; no existe montaje, namespace, ruta de instalación o credencial nueva por este cambio.

El orden reserva → aprobación primaria → comprobación de constancia → transacción final evita presentar un puntero parcialmente instalado. No se adopta ni sobrescribe una aprobación/puntero/reserva existente. La repetición completada requiere el mismo baseline, constancias actuales y aprobación primaria sin revocar. El lector de cierre conserva deliberadamente la lectura de una aprobación revocada para recuperación; esa capacidad no permite al instalador informar éxito.

No existe atomicidad distribuida entre D1 y DO. Una inserción reconocida seguida de fallo se revoca conservando historia. Cuando se pierde la respuesta del INSERT no se conoce su autoría: una fila idéntica no la demuestra. Se conserva `pending`, sin puntero, y se exige conciliación administrativa antes de cualquier habilitación. Un conflicto definitivo tampoco revoca la fila ajena. Si la respuesta de commit DO se pierde, pueden quedar metadatos `complete` y la aprobación propia revocada; es recuperación manual, nunca éxito por el marcador solo. Ninguna recuperación borra D1/DO ni reanuda automáticamente.

## Validación y límites

Las pruebas unitarias usan D1 SQLite real y transacciones de almacenamiento de fixture. La prueba workerd usa D1 y DO SQLite reales, instala/reconstruye/repite y comprueba rollback atómico de una escritura tardía del puntero conservando una fila primaria revocada. El emisor y las constancias de estas pruebas son **sintéticos**, sin datos de clientes. Revisión independiente detectó discrepancia de inscripción al repetir y estado incierto tras respuesta perdida; ambas se reprodujeron y corregieron con pruebas.

El montaje remoto aún requiere un emisor administrativo que compruebe creación real de identidad, custodia cloud correspondiente e inventario exclusivo vigente. Una callback, un hash, el nombre de una variable o un estado `ready` no acreditan esas condiciones. Se debe mantener Access cerrado hasta conciliar la aprobación, el catálogo, enrollment y admisión HTTP. Luego faltan cierre espontáneo remoto verificado, publicación/adopción real del ejecutor cloud y programación de una única ocurrencia. Solo después puede coordinarse el ensayo con el PC apagado. Max y la guardia permanente quedan fuera de esta preparación.
