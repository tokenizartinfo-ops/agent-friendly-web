# Instalador y catálogo propios en el host primario

La fuente del Durable Object existente compone ahora el instalador primario con su productor y D1 ligado a AFW_QA_DB. installOwn no admite payload ni devuelve permisos de inicio/consumo: esos presupuestos permanecen internos y de un solo primer ACK. Cada operación viva incluye el checkpoint conjunto de preregistro, originales, desafío, reserva, propietarios, diario, intención, finalización y consumo.

AFW_QA_INSTALLATION_ENABLED queda cerrado por defecto. Falta de AFW_QA_OCCURRENCE_DISPATCH.dispatch o D1 produce unavailable antes de reservar/escribir. La dependencia de despacho es un binding privado futuro, todavía ausente del runtime: la fuente no fabrica una llamada cloud. El binding propio D1 permite la escritura local propia; no acredita autorización administrativa externa. El despachador real aún deberá comprobar preflight cloud y admisión servidor independientes. dispatch_attempted solo documenta que se llamó al binding. Un timeout no prueba que un servidor canceló su trabajo, y un reintento nunca reconstruye el presupuesto gastado.

readOwnInstallationHistory conserva las referencias documentales. readOwnClosureScope requiere AFW_QA_PRIMARY_CATALOG_ENABLED explícito: compara registro original, aprobación configurada, reserva, holds, intención, finalización y procedencia D1 mediante lecturas independientes y checkpoint primario conjunto. D1 revoked y vencimiento pueden ser situaciones esperadas del cierre propio; no recuperan admisión ni renuevan fechas. Retirada de reserva/preregistro impide autorizar el catálogo. El consumo, si existe, debe validar su enlace a la finalización.

IndependentClosure puede optar por este catálogo en SAME preregistry, sin namespace alternativo ni pointer legacy nuevo. Con el flag cerrado conserva su composición anterior. No hay rutas HTTP administrativas nuevas, migración o despliegue remoto en este bloque.

Prueba nativa: SQLite y D1 locales reales; proveedor, identidad, originales cloud y despachador explícitamente sintéticos. Falta de despachador deja cero filas, dos instalaciones comparten una escritura/consumo/llamada, retry conserva pending sin nuevo despacho, revocación D1 y expiración permiten exclusivamente lectura de cierre, retirada deja catálogo nulo e historial. Esto no acredita permiso externo, adopción cloud, programación ni PC-off.

La revisión detectó que consumptionHistory podía devolver null tanto por ausencia como por registro inválido. La lectura compara ahora presencia y contenido primarios con cada recibo validado; un consumo existente inválido rechaza el catálogo. La prueba reproduce ese rechazo y restaura únicamente su registro sintético. IndependentClosure se monta también en la fixture y consulta el catálogo primario real: unarmed no prueba custodia ni cierre global.
